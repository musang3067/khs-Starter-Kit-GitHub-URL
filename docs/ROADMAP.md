# ROADMAP: 개인 개발 블로그 (Notion CMS 기반)

> 이 문서는 [PRD.md](./PRD.md)를 기반으로 작성된 개발 순서 로드맵입니다.
> 각 단계는 이전 단계의 결과물 위에 쌓이므로, 순서를 건너뛰지 않고 진행하는 것을 권장합니다.

## 전체 순서 요약

| 단계 | 내용 | 예상 소요 시간 |
|---|---|---|
| 1 | 프로젝트 초기 설정 (골격 구축) | 0.5 ~ 1일 |
| 2 | 공통 모듈/컴포넌트 개발 | 2 ~ 3일 |

## 1단계: 프로젝트 초기 설정 (골격 구축)

### 할 작업
- [ ] Next.js 15 + TypeScript 프로젝트 확인 (기존 `create-next-app` 결과물 점검)
- [ ] Tailwind CSS 설정 확인 및 `shadcn/ui` 초기화 (`npx shadcn@latest init`)
- [ ] Lucide React 아이콘 패키지 설치
- [ ] `@notionhq/client` 패키지 설치
- [ ] 폴더 구조 설계 (`src/lib`, `src/components`, `src/types`, `src/app/posts`, `src/app/category` 등)
- [ ] `.env.local` 환경 변수 설정 (`NOTION_API_KEY`, `NOTION_DATABASE_ID`)
- [ ] `.env.local`을 `.gitignore`에 포함 확인
- [ ] ESLint 규칙 점검, 기본 코드 스타일 합의
- [ ] Notion 데이터베이스 생성 (Title/Category/Tags/Published/Status/Content 필드 반영) 및 API 연동 테스트 (글 1개 fetch 성공 여부)

### 왜 이 순서인가
이후 모든 기능이 이 골격(폴더 구조, 스타일 시스템, Notion API 연결) 위에서 개발됩니다. 골격이 흔들리면 2단계 이후 작업을 전부 다시 해야 하므로, 가장 먼저 "환경이 제대로 동작하는지"를 확인합니다.

### 예상 소요 시간
0.5 ~ 1일

### 완료 기준
- `npm run dev`로 로컬 서버가 정상 구동됨
- `npm run lint` 통과
- 테스트 스크립트/페이지에서 Notion API로 데이터베이스의 글 1건을 성공적으로 가져옴
- 민감 정보(API 키)가 git에 커밋되지 않음

## 2단계: 공통 모듈/컴포넌트 개발

### 할 작업
- [ ] Notion API 클라이언트 래퍼 작성 (`src/lib/notion.ts`) — `getPosts()`, `getPostBySlug()`, `getCategories()` 등
- [ ] 타입 정의 (`src/types/post.ts`) — `Post`, `Category`, `Tag` 인터페이스
- [ ] Notion 응답 → 내부 타입 변환 로직 (어댑터/매퍼 함수)
- [ ] 공통 UI 컴포넌트 구축 (`shadcn/ui` 기반): Header, Footer, Layout, Card, Badge(태그), Button
- [ ] 유틸 함수: 날짜 포맷팅, 텍스트 요약(truncate), slug 생성
- [ ] API 에러/로딩 상태에 대한 공통 처리 방식 정의 (에러 바운더리 또는 공통 fallback UI)

### 왜 이 순서인가
핵심 기능(글 목록, 글 상세, 검색 등)은 모두 "Notion에서 데이터 가져오기"와 "UI로 보여주기"를 반복적으로 수행합니다. 이 두 가지를 먼저 공통 모듈로 만들어두면, 3단계부터는 중복 코드 없이 빠르게 기능을 조립할 수 있습니다. 반대로 순서를 바꿔 핵심 기능을 먼저 만들면, 페이지마다 Notion 호출 로직이 중복되고 나중에 리팩토링 비용이 커집니다.

### 예상 소요 시간
2 ~ 3일

### 완료 기준
- `getPosts()`, `getPostBySlug()` 함수가 타입이 지정된 데이터를 정상 반환
- Header/Footer/Layout이 모든 페이지에 공통 적용 가능한 상태
- 더미 데이터로 Card, Badge 등 컴포넌트가 스토리/테스트 페이지에서 정상 렌더링됨

## 3단계: 핵심 기능 개발 (MVP)

### 할 작업
- [ ] 홈 페이지: 최근 글 목록 표시 (`getPosts()` 활용, Card 컴포넌트 재사용)
- [ ] 글 상세 페이지 (`/posts/[slug]`): Notion 페이지 콘텐츠 렌더링 (Notion 블록 → HTML/React 변환, 예: `react-notion-x` 또는 직접 블록 파서)
- [ ] 기본 라우팅 구조 확정 (정적 생성 `generateStaticParams` 또는 ISR 고려)
- [ ] Status가 "발행됨"인 글만 노출되도록 필터링 로직 적용
- [ ] 기본 스타일링 (Tailwind 기반, 타이포그래피 플러그인 고려)
- [ ] 반응형 레이아웃 1차 적용 (모바일/데스크톱 기본 대응)

### 왜 이 순서인가
PRD의 MVP 범위(글 목록 + 상세 페이지)에 해당하는, 블로그의 핵심 가치를 구현하는 단계입니다. 공통 모듈이 준비된 상태이므로 여기서는 "조립"에 집중할 수 있습니다. 검색/필터 같은 부가 기능보다 먼저 "글을 읽을 수 있다"는 가장 중요한 경험을 완성합니다.

### 예상 소요 시간
3 ~ 5일

### 완료 기준
- 홈에서 발행된 글 목록이 실제 Notion 데이터로 노출됨
- 글 클릭 시 상세 페이지에서 본문 콘텐츠(텍스트, 이미지, 코드블록 등)가 깨지지 않고 표시됨
- 모바일/데스크톱 화면에서 레이아웃이 깨지지 않음
- 초안(Status=초안) 글은 노출되지 않음

## 4단계: 추가 기능 개발

### 할 작업
- [ ] 카테고리별 필터링 페이지 (`/category/[category]`)
- [ ] 검색 기능 (클라이언트 사이드 필터링 또는 서버 사이드 검색)
- [ ] 태그 표시 및 태그 기반 탐색(선택)
- [ ] SEO 메타데이터 (`generateMetadata`, Open Graph 이미지 등)
- [ ] 페이지네이션 또는 무한 스크롤 (글이 많아질 경우)
- [ ] 다크모드 지원 (선택, shadcn/ui 테마 활용)
- [ ] 반응형 디자인 2차 개선 (세부 브레이크포인트, 접근성 보완)

### 왜 이 순서인가
PRD에 명시된 "카테고리별 필터링"과 "검색 기능"은 MVP가 안정적으로 동작한 뒤에 추가해야 합니다. 핵심 읽기 경험이 흔들린 상태에서 필터/검색을 먼저 만들면, 기반 로직이 바뀔 때마다 필터링 코드도 다시 손봐야 하는 비효율이 생깁니다.

### 예상 소요 시간
3 ~ 4일

### 완료 기준
- 카테고리 페이지에서 해당 카테고리 글만 정확히 필터링됨
- 검색 시 제목/내용 기준으로 관련 글이 노출됨
- 각 페이지에 적절한 `title`/`description` 메타데이터가 설정됨
- Lighthouse 접근성 점수 90점 이상 (선택 목표)

## 5단계: 최적화 및 배포

### 할 작업
- [ ] 이미지 최적화 (`next/image` 적용, Notion 이미지 URL 처리)
- [ ] 데이터 캐싱/재검증 전략 수립 (ISR `revalidate` 주기 또는 on-demand revalidation)
- [ ] Lighthouse로 성능/접근성/SEO 점검 및 개선
- [ ] 에러 페이지(404, 500) 커스터마이징
- [ ] Vercel 프로젝트 연결 및 환경 변수(Production) 설정
- [ ] 커스텀 도메인 연결 (선택)
- [ ] 배포 후 실제 Notion 글 작성 → 반영 확인 (엔드 투 엔드 검증)
- [ ] 기본 모니터링/로그 확인 (Vercel Analytics 등, 선택)

### 왜 이 순서인가
기능이 모두 완성된 후에 성능 최적화와 배포를 진행해야, 불필요한 재작업 없이 "완성된 기능"을 기준으로 최적화할 수 있습니다. 너무 일찍 최적화를 시작하면 이후 기능 변경 시 최적화 작업을 다시 해야 할 수 있습니다.

### 예상 소요 시간
2 ~ 3일

### 완료 기준
- Vercel에 배포된 URL에서 모든 페이지가 정상 동작
- Notion에서 새 글 작성 후, 설정한 재검증 주기 내에 블로그에 자동 반영됨
- Lighthouse 성능 점수 85점 이상 (목표치, 조정 가능)
- 404/500 등 에러 상황에서도 사용자 친화적인 페이지 노출
